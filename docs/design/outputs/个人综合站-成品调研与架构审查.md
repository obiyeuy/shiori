# 个人综合站：成品调研与架构审查

调研日期：2026-09-25。本文是选型调研，不是已批准的实施规格，不包含部署操作。

## 结论

整体方向可行：网站内容放 MySQL，媒体文件单独挂载持久目录，通过子域名提供访问。现有服务器服务保持不变。

但还不能直接进入实现。关键未决项是采用成品还是自建、哪些私人功能纳入第一版、认证方式和内容发布语义。框架尚未正式选定，前面讨论的 SvelteKit、Astro 都是候选。

推荐先评估 **Halo 社区版 + 免费插件 + 合适主题**，因为它最接近已经描述的公开个人站。若私人工作台、复杂工具和统一交互必须成为首版核心，再选择 **SvelteKit 全栈应用 + MySQL**。不建议为节省表面上的后台开发量，贸然叠加多个 CMS、搜索和文件服务。

没有在本轮核实的候选中发现一个无需扩展、同时覆盖公开文章/笔记/动态/作品/工具/收藏以及完整私人任务、日记、文件工作台的成品。成品能明显降低公开站建设成本，但不能把“支持插件”当作已经实现全部需求。

## 1. 已确定的约束

- 内容为主的个人综合站，个人介绍少，文章、笔记、动态区分展示。
- 包含作品和工具，资源收藏纳入规划。
- 文章等内容以数据库为正式来源，不以本地 Markdown 文件为主库。
- 文章正文倾向保存 Markdown，支持导入导出。
- MySQL 独立容器，网站独立容器，可在一个 Docker Compose 项目下管理。
- 图片、附件保存为服务器文件并挂载到容器。正文可以引用稳定的站内相对路径，不要求媒体 ID 路由。
- 私人日记、任务、文件需要另行设计权限，不能默认为公开媒体。
- 使用子域名，具体域名未确定。
- 尽量不增加软件订阅、图床和云存储费用。
- 不影响服务器现有服务；不执行批量文件删除或目录删除。

尚未确认：公众注册、评论方式、管理员认证、私人功能首版范围、可接受的数据丢失时长和恢复时间。

## 2. 调研方法与局限

核对官方安装、数据库、发布、媒体和备份文档，阅读项目官方 README 与部分公开源码，检查 GitHub 最新正式发布信息。没有安装候选产品，没有修改服务器服务，没有进行负载测试或完整迁移演练。

本轮只读复查服务器：x86_64，4 个逻辑 CPU，约 3.6 GiB 内存，可用内存快照约 2.8 GiB；40 GB 根盘剩余约 9.8 GB。现有四个运行容器在检查时占用内存较低，但这是瞬时状态，不能代表 PDF 处理或其他任务的峰值。

GitHub 正式发布接口返回：Halo v2.26.1（2026-09-01）、Typecho v1.3.0（2026-01-20）、Ghost v6.65.0（2026-09-22）、Strapi v5.55.1（2026-09-24）、Directus v12.4.1（2026-09-23）。发布活跃度不等同于质量或兼容性保证。实施应固定经过验证的版本，不使用浮动 latest。

### 3.1 Halo：最贴近公开站，但不是全部功能现成

可以对应你的需求：

- 文章与笔记：用分类、元数据和独立列表模板区分；后台未必天然是两种独立内容模型。
- 动态：plugin-moments 提供图文、音视频内容及列表/详情路由。
- 作品：自定义页面、文章模板或扩展模型，取决于作品字段复杂度。
- 友链和资源：plugin-links 有分组、描述、排序等能力；“推荐资源”的展示可再调整。
- 图片：内置本地附件存储，与 Docker 挂载兼容。
- 工具：仅在浏览器运行的工具可集成主题页面；依赖后端的工具需要插件或服务接口，不能笼统说全部开箱即用。

需要核实的边界：

1. 插件装好不等于前台自动出现。Moments 和 Links 的文档明确要求主题模板适配。
2. 当前社区版免费，专业版、部分主题和插件收费。内置手动备份/恢复可用，官方“备份增强插件”的自动备份与同步标明付费版专享。可以另行设计免费运维备份，但要承担维护工作。
3. 文章文档提供作者私有内容选项；这不证明附件 URL 同时私有，也不等于完整私人空间。“全站私有化”在版本对比中属于付费功能，与局部私有文章不是一回事。
4. 官方 Docker 文档默认示例可能使用 halo-pro，需要明确选择社区版镜像。示例中的数据库版本和 root 账号也不能原样照抄到正式环境。
5. Halo 自 2.0 使用扩展资源模型。数据库不是简单的 articles、tags 表组合；源码 Snapshot 中保存源格式及内容/源文的快照或差异。迁移应使用受支持的 API、备份或导出方式，不直接绑定内部表结构。
6. 文档说明附件“移动”只支持分组移动，不等于跨存储策略迁移。因此从本地改对象存储仍要检查链接和文件迁移。

参考：[部署](https://docs.halo.run/guide/install/docker-compose)、[文章](https://docs.halo.run/guide/use/posts)、[附件](https://docs.halo.run/guide/use/attachments)、[备份](https://docs.halo.run/guide/use/backup)、[版本对比](https://www.lxware.cn/halo)、[ByteMD](https://github.com/halo-sigs/plugin-bytemd)、[动态](https://github.com/halo-sigs/plugin-moments)、[链接](https://github.com/halo-sigs/plugin-links)、[数据库模型说明](https://docs.halo.run/guide/faq)。

### 3.2 WordPress：后台成熟，采用它就接受它的内容约定

WordPress 自托管软件免费，不等于所有主题和插件免费。公开内容管理、修订和媒体管理成熟，可自定义作品等内容类型。

它默认使用块编辑器，Markdown 输入快捷方式不代表正文以纯 Markdown 保存。若纯 Markdown 是硬要求，必须验证编辑、保存、再编辑和导出的完整往返过程。

自建在线工具可以通过自定义插件/页面接入，但持续做复杂前端应用时，开发方式受 WordPress 主题和插件架构影响。普通私密文章不能代替私人附件访问控制。

WXR/XML 导出记录内容和附件相关信息，不能视为包含实际图片文件、主题和配置的完整备份。域名也可能保存在正文和配置里，迁移要采用产品支持的替换流程，不能假定所有链接自动保持相对形式。

参考：[功能](https://wordpress.org/about/features/)、[Docker](https://github.com/docker-library/docs/blob/master/wordpress/README.md)、[导出](https://wordpress.org/documentation/article/tools-export-screen/)、[迁移](https://developer.wordpress.org/advanced-administration/upgrade/migrating/)。

### 3.3 Strapi：省后台，但不是两容器完整成品

Strapi 可以为文章、笔记、动态、作品定义数据模型，有 Markdown 字段、媒体库和 Draft & Publish。前台仍需要 SvelteKit、Astro 或其他框架开发。通常形成前台、Strapi、MySQL 三个服务；不要为了保留“两容器”而把进程硬塞在一起。

免费边界：媒体库和草稿发布是免费功能；内置 Content History 当前属于 Growth/Enterprise。草稿与已发布版本分离，不等于拥有可回退的完整历史版本。

默认本地上传位置为 public/uploads，不能直接用于私人文件。需要受保护的存储/接口实现。

官方部署文档给出内存最低 2 GB、推荐 4 GB+。这不是常驻内存实测，但意味着你这台已有其他服务的约 3.6 GiB 主机，不能未经测量就承诺再加前台、MySQL 和 Strapi 后一定宽裕。

参考：[数据库](https://docs.strapi.io/cms/configurations/database)、[内容建模](https://docs.strapi.io/cms/features/content-type-builder)、[发布](https://docs.strapi.io/cms/features/draft-and-publish)、[媒体](https://docs.strapi.io/cms/features/media-library)、[上传提供者](https://docs.strapi.io/cms/configurations/media-library-providers)、[历史版本](https://docs.strapi.io/cms/features/content-history)、[部署要求](https://docs.strapi.io/cms/deployment)。

### 3.4 其余候选的限制

- Typecho：官方明确 Markdown、主题、插件与 MySQL 支持，适合博客基础；未核实到满足私人工作台全部要求的官方组合。官方 README 的最低环境版本不是生产环境版本推荐。
- Ghost：目前官方 Docker 安装文档仍标注该套安装工具为 preview，带 Caddy、MySQL 及可选服务。发布和订阅是优势，你没有明确需要会员付费或邮件订阅平台。
- Directus：支持 MySQL、Docker 持久化及带权限的文件 API，但公开站仍需开发。旧 BSL 地址本次跳转到 MSCL-1.0-GPL 授权页面，不能沿用过去的“收入门槛免费”结论；需按具体版本和功能重新核对。文件 URL 采用 ID 是它的产品设计，不是所有网站必须如此。
- Payload：官方数据库适配器列 MongoDB、PostgreSQL、SQLite，没有 MySQL。当前不值得为了接入它另造数据库适配器。

参考：[Typecho](https://github.com/typecho/typecho)、[Ghost Docker](https://docs.ghost.org/install/docker)、[Ghost 数据库](https://docs.ghost.org/faq/supported-databases)、[Directus 数据库](https://directus.com/docs/configuration/database)、[Directus 文件访问](https://directus.com/docs/guides/files/access)、[Directus 授权](https://directus.com/license)、[Payload 数据库](https://payloadcms.com/docs/database/overview)。

## 4. 当前方案的具体问题和优化

### 4.1 发布版本不应被自动保存覆盖

如果只保存一个 body_markdown 并标记 published，编辑已发布文章时自动保存可能直接改掉线上正文。应把编辑稿和公开版本分开；发布操作更新公开版本，刷新对应页面、列表、RSS 和搜索缓存。以版本号检查多标签页修改冲突。

自建时可使用内容主记录、版本记录、当前编辑版本与当前发布版本引用；成品则复用其发布模型。不要为了统一而绕过 CMS 自己的 API 直接修改表。

### 4.2 数据模型既不要六套重复系统，也不要一张万能表

文章、笔记和作品共用标题、slug、正文、发布时间等基本能力，类型特有字段单独扩展。动态、任务、用户、附件独立建模。私有数据的查询必须从服务端权限开始，不能只在前端隐藏。

公开页面、搜索、RSS、站点地图和附件都需要一致的公开规则。复杂权限不等于必须另建一套账号服务；首版单管理员是建议，尚未得到用户明确确认。

### 4.3 数据库存内容不必每次发布重新构建网站

自建路线建议内容页采用服务端 HTML 输出，按需增加公开页面缓存。稳定的说明页可预渲染。发布是更新内容和缓存，部署是更新代码，两者分开。

MySQL 已成为内容来源后，Astro 的文件内容集合优势不再是主要选择依据。若继续自建，SvelteKit 在后台与工具共用组件方面更贴近需求；Astro 仍可实现，不存在必须换框架的技术障碍。

### 4.4 图片挂载解决持久化，不解决全部迁移与权限问题

保留用户接受的模式：正文引用 /media/2026/09/唯一文件名.webp；本地根目录由部署配置和挂载决定。数据库只存相对文件键、类型、大小、尺寸、所有者和可见性，不保存主机绝对目录。

容器重建时挂载可保留文件，但媒体目录不是备份；没有复制文件，换服务器仍会断图。相对 URL 适用于站内页面，RSS、邮件、分享图等需要根据当前站点地址生成绝对 URL；导出 Markdown 时应将图片打包并转换链接。

公开媒体可以缓存。私人附件不能直接暴露为静态目录；草稿图片默认受保护，发布时建立公开副本或受控公开映射，避免复用文件时误公开私人附件。已公开图片不能承诺从访客缓存中撤回。

原图处理之前说得过于武断：不默认进行不可逆的有损替换。照片可以生成展示版，截图优先保留文字清晰度和透明背景；是否保留原图需要结合空间预算决定。禁止默认把 SVG/HTML 当可安全内联的普通图片，上传限制应覆盖格式、字节数和像素尺寸。

### 4.5 恢复能力比“可以迁移”更具体

备份对象应包含数据库一致性导出、媒体、必要配置、应用版本/数据结构版本，以及单独安全保存的密钥。数据库备份不能简单复制正在写入的 MySQL 数据目录。

个人站可在短暂维护窗口暂停写入后创建配套备份，或使用快照/一致性机制。之后在独立测试环境恢复，核对文章、图片、草稿和私人权限。成品内容导出不等于整站灾难恢复包。

另提供通用导出：Markdown 正文 + JSON 元信息 + 图片目录 + 引用清单，避免只保留 SQL dump 后难以更换产品。

备份至少一份离开服务器，可使用用户已有 Mac。Mac 离线时要记录失败，不能把定时任务存在当作备份成功。本阶段不配置自动批量清理；需保留多代时设置容量告警，清理对象由用户核对处理。

### 4.6 MySQL 和 Docker 的边界

- 数据库不发布公网端口；应用账号仅访问本站数据库，不用 root。
- 使用正式受支持的数据库版本，产品兼容后固定版本；utf8mb4 保存中文和 emoji。
- Compose 项目名、网络、数据卷和目录独立，资源限制要在测量后确定。
- 设置健康检查、连接重试、小规模连接池；MySQL 可用不等于业务迁移已完成。
- 备份后才升级数据结构。旧镜像并不能自动回滚已经变化的数据库。
- 构建不占用现有服务器峰值资源；Mac 构建必须匹配服务器 linux/amd64，不能把 macOS node_modules 直接拷过去。
- 不执行 Docker prune 或其他违反用户删除限制的清理操作。

### 4.7 搜索、工具和任务的范围

先做标题、标签、摘要搜索和分页；若使用 MySQL 全文搜索，中文分词须选 ngram 等合适方式并用真实中文样例验证。没有证据表明首版需要 Elasticsearch、向量数据库或图数据库。

在浏览器内完成的工具优先本地处理；长耗时转换、AI 调用等不能无上限占用网站请求进程，出现具体需求时再增加任务处理机制。展示一个工具入口与维护一个计算服务不是同等工作量。

私人日记/任务/文件属于后续独立功能规格，保留范围但分阶段建设，避免把 CMS 选型扩大成一口气开发完整个人办公系统。

## 5. 推荐的选择顺序

### 路线 A：Halo 社区版优先评估

适合尽快获得可维护的公开站。使用社区版、免费插件与主题，MySQL 和工作目录分别持久化。公开站定制通过主题与插件完成，不修改核心源码。私人任务和文件管理后续单独设计。

必须验证的最小场景：一篇带代码/表格/图片的 Markdown 文章；一篇笔记；一条图文动态；一个作品页面；一个浏览器工具；手机阅读；备份到另一套实例后恢复。额外检查私人内容和附件直链。只有这些通过，才认为“成品适合”。

### 路线 B：自建 SvelteKit + MySQL

适合统一界面、自定义编辑与私人工作台是核心诉求的情况。可复用成熟编辑器、Markdown 渲染与认证组件，但仍需承担发布模型、媒体权限、迁移、测试和备份恢复的开发。

容器数量少不是开发工作量少的证据。只做首版真正使用的模块，后续扩展保留数据边界。

### 路线 C：定制前台 + Strapi

适合需要复杂内容模型和现成管理后台，且接受额外服务与免费功能边界的情况。考虑本机资源和私人文件需求，优先级低于前两条。数据库由 Strapi 独占管理，前台通过 API 访问，不再自建另一套直连写入逻辑。

## 6. 进入实现前的验收条件

- 明确路线、首版范围和管理员登录方式。
- Markdown 编辑、保存、重新打开、导出不丢公式/代码/图片引用。
- 修改已发布内容后，未发布草稿不会出现在公开接口、搜索、RSS 中。
- 私人文件直链、缩略图和缓存均不能绕过权限。
- 重建容器不丢内容；整站备份可在独立环境恢复。
- 检查真实移动端页面、图片上传失败、磁盘不足、数据库暂不可用等情况。
- 测试资源占用及现有服务高峰期间的余量，再确定部署限制和入口方案。
