## 1. 项目目标

用户计划搭建一个自建的个人综合站。它以内容为中心，同时承载个人能力与作品展示、结识同好、个人开发的小工具入口，以及后续的私人功能。

它不是传统简历页，也不是单纯博客。个人介绍需要克制，主要通过文章、笔记、作品、动态和工具体现个人方向。

### 公开栏目

- 首页：简短定位、近期更新、精选内容和工具/作品入口。
- 文章：较完整、正式的长文。
- 笔记：知识整理、技术记录和短篇内容。
- 动态：更随性的近期记录，与正式文章分开。
- 作品：代码、实验、创作和项目介绍。
- 工具：自己开发的工具以及已有服务的入口。
- 资源：收藏、参考资料等；有实际内容后再重点展开。
- 关于：简短介绍、联系方式、站点说明。

### 后续私人功能

- 日记
- 任务
- 私人文件
- 其他只有站长可见的功能

私人功能要单独设计权限，不通过前端隐藏来实现安全边界。

## 2. 已确认的总体产品方向

- 首版只有一个站长，不开放公众注册。
- 访客无需登录即可查看已发布公开内容和公开工具。
- 站长登录后可以管理内容、媒体、评论设置和私人服务入口。
- 正式内容和随性动态保留，但栏目明确区分。
- 内容支持标签，也可以组织为系列/专题。
- 标签由作者手动选择；系统只做已有标签补全、重复提示和最近使用提示，首版不自动生成标签。
- 系列内部阅读顺序由作者手动调整，不由发布时间自动决定。
- 评论使用官方 Giscus，不自建评论服务。
- 现有服务器 Docker 服务与网站共存，首版只做登录后的入口卡片，不做深度 API 集成或 Docker 控制。

## 3. 已确认的 UI 方向

用户已选择 **A＋C 混合布局**：

### 公开站：A，内容优先

- 顶部导航。
- 首页打开后直接看到文章、笔记、动态、作品和工具内容。
- 个人介绍只保留一句定位、头像/角色视觉和近期更新，不放大段自传。
- 栏目多时通过二级筛选、搜索和内容卡片组织，不把所有东西塞进巨大首屏。

### 登录后空间：C，公开站与个人空间分开

- 登录后进入独立的个人空间首页。
- 个人空间承载管理后台、服务入口和未来的私人功能。
- 桌面端使用工作台式侧栏；移动端改为抽屉导航。
- 私人空间与公开首页共享品牌，但信息层级和背景色不同。

### 视觉风格：二次元、活泼、生动

用户明确表示不要极简风。目标是轻二次元创作者网站：有角色感和活泼气质，但不能让装饰影响长文阅读，也不要做成幼儿化卡通站。

建议视觉语汇：

- 圆角卡片、彩色标签、贴纸式徽章。
- 局部不对称构图、细线描边、柔和阴影。
- 首页、空状态、工具卡片中使用少量星星、波纹、网点和角色插画。
- 正文、代码块、目录和评论区保持安静、稳定、可读。
- 动效以按钮反馈、卡片抬升、轻微淡入为主，禁止持续晃动或复杂滚动特效。

## 4. 技术架构

```text
Cloudflare Tunnel / 后续验证的入口
        ↓
SvelteKit Web 容器
├── 公开页面
├── 管理后台
├── Markdown 编辑器
├── 登录与权限
├── 搜索与工具入口
└── 文件上传接口
        ↓ Docker 内部网络
PostgreSQL 容器

宿主机持久目录
├── PostgreSQL 数据
├── media/public
├── media/private
└── backups
```

### 已确认的技术选择

- 自己开发，不使用 Halo。
- 技术栈：SvelteKit + PostgreSQL。
- Web 与 PostgreSQL 在同一个独立 Docker Compose 项目中，但使用不同容器。
- 浏览器不直接连接数据库，所有数据库访问经过 SvelteKit 服务端。
- PostgreSQL 不开放公网端口。
- 首版保持一个 SvelteKit 全栈应用，不拆成独立前端和后端仓库。
- 不提前加入 Redis、Elasticsearch、向量数据库、图数据库、MinIO 等基础设施。
- 内容发布与代码部署分开。
- 公开稳定页面可预渲染；动态页面和管理页按需服务端处理。

## 5. 数据和媒体方案

### 正式内容

- PostgreSQL 是文章、笔记、动态、作品、资源和工具说明的正式来源。
- 正文保存为 Markdown 文本。
- HTML 是渲染输出，不作为正文原件保存。
- 内容数据、发布状态、标签关系、系列关系、版本和排期存数据库。
- 首版不把本地 `.md` 文件当作线上正式内容源，但应支持 Markdown 导入和导出，方便迁移。

### 媒体

- 图片、视频、PDF 和其他附件保存到宿主机持久目录，由 Web 容器挂载使用。
- 数据库存媒体元数据，不默认存图片二进制。
- 文章中保存站内相对媒体引用，例如：`/media/2026/09/example.webp`。
- 绝不保存宿主机绝对路径。
- `media/public` 和 `media/private` 分开；私人附件不能直接作为公开静态目录。
- 默认保留上传原图，需要时生成展示图/缩略图；不覆盖原图。
- 支持粘贴、拖拽和文件选择上传。
- 不自动删除未引用媒体、原图或历史版本；先监测容量。
- 历史版本引用的媒体不能当成未使用媒体。
- 未来迁移依赖媒体文件键、数据库元数据和通用导出，不依赖服务器目录结构。

### 图片展示约束

- 照片、截图、透明 PNG、动画图片要有不同的处理策略。
- 允许限制过大尺寸，但不能简单地把所有图片压缩成低质量缩略图。
- 需要设置单图和总量限制，并在后台显示容量提示；阈值待资源测试后确定。
- 图片加载前预留 `aspect-ratio`，避免布局跳动。

## 6. 编辑、版本和发布

### Markdown 编辑器

用户已明确选择 Markdown，而不是 Word 式可视化编辑器。

首版计划支持：

- CommonMark 基础语法。
- 表格、任务列表、删除线。
- 代码高亮和复制按钮。
- 自动生成文章目录。
- 数学公式。
- Mermaid 图。
- 脚注。
- 图片粘贴、拖入和上传状态。
- 桌面端编辑/预览并排；移动端编辑/预览切换。
- 独立整页预览。

具体编辑器、Markdown 解析器、语法高亮库和 Mermaid 渲染库尚未决定。预览和公开页面必须使用一致规则，不能允许 Markdown 执行任意脚本。

### 草稿和版本

- 自动保存只更新编辑稿，不直接改变公开版本。
- 手动保存、设置/更新排期和正式发布时，保留不可变版本快照。
- 不把每次键盘输入都保存为历史版本。
- 可按间隔保存草稿检查点，具体间隔和容量待定。
- 历史版本可查看时间、比较差异和恢复。
- 恢复旧版本会生成新的编辑稿，不改写历史，不自动覆盖当前线上版本。
- 有效排期不会因恢复历史版本而隐式改变。
- 版本至少覆盖标题、正文、摘要、标签、封面、媒体引用和相关发布字段。

### 定时发布

- 首版支持定时发布。
- 管理界面默认显示北京时间 `Asia/Shanghai`，数据库保存带时区时间点。
- 排期保存在 PostgreSQL，不能只放在进程内存中。
- 排期绑定一个明确版本；继续编辑草稿不会自动改变待发布版本，需要显式更新排期内容。
- 可以修改时间、取消排期或立即发布。
- 正常运行目标是到期后 1 分钟内发布，不承诺秒级。
- 服务停机错过时间后，恢复时自动补发仍有效的排期。
- 失败排期保留并显示原因。
- 首版可以由 SvelteKit 应用内轻量轮询处理，不新增 Redis 或消息队列；执行必须有事务和并发保护，防止重复发布。

## 7. 标签与系列

### 标签：已确认

- 作者手动选择标签。
- 系统提供已有标签补全、相似标签提示、最近使用记录和重复提示。
- 首版不自动生成或公开应用 AI 标签。
- 标签可选，建议每篇 2–5 个，不作为硬性发布限制。
- 标签负责主题、技术和对象；内容类型负责文章/笔记/动态等；系列负责关联内容和阅读顺序。
- 标签是独立实体，与内容多对多关联。
- 草稿标签修改在发布版本生效，避免提前改变线上展示。
- 去除首尾空白，统一重复空白；拉丁字母大小写用于重复检查，但显示名称保留标准写法。
- 缩写和近义词由作者确认关联，系统不自动合并。
- 标签重命名保留实体 ID；若公开地址变化，旧地址保留跳转。
- 公开标签页和统计只统计已发布公开内容。

### 系列：部分确认

- 支持系列/专题。
- 系列内部顺序由作者手动调整。

仍需决定：

- 系列是否允许混合文章和笔记。
- 一篇内容是否可以属于多个系列。
- 系列是否有草稿、公开、归档状态。
- 是否有封面、公开进度和完成度展示。
- 排序交互具体采用拖拽、序号还是上下移动。
- 不得把私有或草稿数量泄露到公开进度中。

## 8. 搜索

已确认第一版支持中英文关键词搜索，暂不增加独立搜索服务。

搜索字段：

- 标题。
- 标签。
- 摘要。
- 正文。
- 动态内容。
- 作品介绍。
- 资源说明。
- 工具名称和说明。

结果要求：

- 显示类型、标题、摘要或命中片段。
- 支持按内容类型和标签筛选。
- 标题匹配优先。
- 公开搜索只查已发布公开版本。
- 草稿和私有内容只在受保护后台搜索，不写入公开索引。
- 首版不搜索 PDF 内文、不做图片 OCR。

实现上优先验证 PostgreSQL 的合理方案。中文检索不能直接假定默认全文分词可用，应使用代表性中英文样例测试索引和排序后再定。

## 9. 认证、权限和评论

### 管理员认证

- 首版同时支持账号密码和 GitHub 登录。
- 两种登录进入同一个站长账户。
- 不开放公众注册。
- 第一个 OAuth 登录者不能自动成为管理员。
- 密码账号通过部署初始化流程创建。
- GitHub 身份通过预先绑定关系或允许名单识别。
- 使用成熟密码哈希和服务端会话机制。
- 登录失败限速。
- Cookie 使用 HttpOnly、Secure 等安全属性。
- 写操作执行必要的来源/CSRF 检查。
- 账号恢复建议由服务器管理命令完成，不把邮件系统作为首版必需依赖。

仍需设计：会话期限、GitHub OAuth 绑定和解绑流程、GitHub 账号更换、恢复命令细节、审计日志。

Google 登录和 Passkey 暂不纳入首版。

### Giscus 评论

- 使用官方托管的 `giscus.app`，不自建 Giscus 容器。
- 评论存于 GitHub Discussions，不存 PostgreSQL。
- 需要一个独立公开评论仓库、启用 Discussions 和安装 Giscus GitHub App；实施阶段再创建和配置。
- 每个公开内容页面对应一个稳定 Discussion 标识，不只依赖会变动的标题。
- 评论失败不能阻断正文阅读。
- 草稿和私人内容不加载评论。
- 文章、公开笔记、作品详情默认开启，每篇可独立关闭。
- 动态、工具和资源默认关闭，需要时再开启。
- 评论仓库与网站源码仓库可以分开，网站源码无需公开。
- Giscus 评论不包含在 PostgreSQL 备份中，后续需用 GitHub API 单独导出；导出副本不保证无损恢复原作者、时间和反应信息。

## 11. 备份与迁移

- 异地备份位置使用用户现有 Mac，不新增付费存储服务。
- 服务器每天生成 PostgreSQL 一致性备份。
- Mac 在线时每天拉取；Mac 离线后恢复联网时补拉遗漏的可用备份。
- 媒体按不可变文件键增量复制。
- 不使用会把服务器误删传播到备份的镜像删除同步。
- 复制和校验完成后才能标记备份成功。
- 备份集包含数据库、媒体清单、媒体文件、应用/结构版本和必要配置。
- 密钥单独加密保存，不能进入公开仓库和日志。
- 不自动批量清理历史备份；容量不足时提醒人工处理。
- 首次上线前在隔离环境做恢复验证，不能覆盖现有线上服务。
- 服务器备份成功时间和 Mac 最近拉取时间要可见。
- 初步恢复点目标约为一天，但 Mac 离线会扩大整机损失窗口，不能承诺严格一天内恢复。
- Giscus 需要独立导出方案。

当前只记录设计，不创建定时任务。

## 13. 新会话继续顺序

新会话不要直接开始编码。推荐继续顺序：

1. 先确认二次元视觉强度：轻量装饰、明显角色主题，还是更强的动漫视觉；是否需要固定吉祥物/角色。
2. 确定公开站首页线框：欢迎区、最近更新、精选内容、作品、工具和页脚的优先级。
3. 确定系列规则：是否混合文章/笔记、一篇内容能否属于多个系列、公开状态和排序交互。
4. 细化统一内容模型：文章、笔记、动态、作品、资源和工具是否共用基础表，哪些字段独立。
5. 细化版本、排期、标签关系和媒体引用的数据模型。
6. 细化管理员认证：初始化、GitHub OAuth 绑定、会话、恢复和审计。
7. 选择 Markdown 编辑器、解析器、代码高亮、数学公式、Mermaid 和脚注实现。
8. 设计草稿媒体访问、私人附件、公开媒体 URL、原图和派生图关系。
9. 细化公开页面、后台页面、搜索和服务入口的路由信息架构。
10. 细化 Compose、PostgreSQL 迁移、资源限制和 Cloudflare Tunnel 接入。
11. 细化备份、恢复、监控、错误处理、测试和验收标准。
12. 把所有决策整理成正式设计规格，交用户审阅和批准。
13. 只有用户批准正式规格后，才进入 `writing-plans`，再开始实现。
