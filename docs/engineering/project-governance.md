# 项目治理规则

状态：当前规范。适用范围：代码、数据库、运行脚本、文档和 Git 分支的长期演进。

本文件只记录可跨阶段复用的规则。一次性审查结论、阶段分支名称、验证快照和待决定事项留在对应的验证、设计或历史文档中。

## 架构原则

- 按业务职责划分模块，保持路由、业务规则、数据库访问、外部服务和展示逻辑的边界清晰。
- 业务规则应有明确归属；同一规则的不同入口必须复用同一契约和校验。
- 只为真实的替换、独立演进或测试需求建立抽象，不为了模式、行数或想象中的未来需求增加层级。
- 代码重复只有在语义和变化方向一致时才抽取；相似但语义不同的流程保持显式实现。
- 保持服务端、客户端、数据库和外部服务边界清晰，敏感配置不得进入客户端依赖图。
- 框架约定的入口与项目自定义服务分开记录；同一能力只能有一个可用于生产的权威入口。
- 发布、撤回和排期的生产入口是 `PublicationService`；repository 层的 fixture/read-model 辅助方法不得被路由或 worker 当作生产发布契约。
- 发布、可见性、编辑、排期、媒体处理和认证等状态必须分别建模，事务边界应覆盖业务不变量和外部副作用的可观测结果。

## 删除和简化原则

- 不因“以后可能有用”长期保留无引用、已替代、已过期或重复的代码、文档和分支。
- 删除、合并或移动前检查普通引用、动态引用、框架自动发现、脚本入口、文档链接和 Git 历史。
- 能够合并的文件、模块、文档和分支，优先形成清晰的单一来源。
- 历史记录放入明确的历史或归档位置，不伪装成当前规范；必要时保留提交、标签或恢复说明。
- 删除必须有明确范围、证据和回退方式，不得影响真实业务数据、数据库、媒体、备份、密钥或唯一恢复点。
- 清理工具、构建脚本和 Git 操作同样遵守项目的单文件删除限制：禁止批量删除文件或删除目录，不得拆成连续单文件删除来绕过限制。需要此类清理时提供明确对象清单，交由用户手动处理；继续完成不依赖删除的工作。
- 分支整理须另行核对授权和提交关系；不得把分支整理授权解释为允许清理工作区文件或目录。

## 文档原则

- 当前规范、架构决策、工程说明、运维手册、验证报告、历史记录和草案必须区分，并在文档开头标明状态与适用范围。
- 同一主题尽量只有一个当前维护入口；导航页必须指向该入口并说明其他文件是历史、证据或草案。
- 计划完成后不能继续以“待审阅”或“待实施”作为当前状态；验证报告记录证据快照，不替代当前规范。
- 文档变更同步修复导航和内部链接；历史绝对路径只能作为追溯信息，不能作为运行入口。
- 文档服务于当前维护。重复、冲突或无维护价值的内容应提出合并、改写、归档或删除方案，并保留不丢失信息的回退路径。
- 代码、脚本、配置和文档出现状态冲突时，以当前代码和可复现验证为事实来源，并在导航中明确偏差。

## 分支原则

- `main` 是当前可验证状态的唯一主要来源；远程 HEAD 应与其一致。
- 分支粒度必须匹配独立交付价值。小修改不创建长期分支，阶段性分支完成合入后及时清理或转为明确的历史标签。
- 分支名称必须反映实际内容；已完成的 feature、阶段快照和重复别名不得继续作为活跃开发分支。
- 保留备份分支时必须写明用途、恢复点和负责人；备份分支不能替代清晰提交历史和验证文档。
- 清理前核对 `merge-base`、独有提交、`--contains`、文档/脚本引用以及本地与远程差异；不得删除主分支、受保护分支或仍有独有价值的提交。
- 不改写共享历史。远程同步使用普通删除或推送，禁止以 force push 代替整理。

## 重构原则

- 先建立对外行为和业务不变量的验证，再进行高风险重构。
- 优先渐进式重构：每阶段有明确范围、前置条件、验证方式和回退方法。
- 重构保持现有行为，除非行为变化已明确确认；新增范围不得默默并入当前阶段。
- 先统一权威契约和入口，再拆分模块或引入扩展机制；避免透传层和万能工具模块。
- 删除被替代的旧实现前，确认没有路由、脚本、测试或动态加载引用，并保留可恢复历史。

## 变更审查最低要求

每项结构性变更应说明：真实变化场景、当前修改路径、最小方案、维护成本、回归风险、验证命令、验收标准和回退方式。审查结论分为“已确认”“有依据但待验证”和“可选改进”，不得把风格偏好写成风险问题。

## 页面深度优化规则

- 页面优化按页面职责、用户任务和数据状态推进，不以统一套模板或单纯增加视觉效果为目标。
- 每个页面先建立当前行为基线：入口、主要任务、数据来源、权限、空状态、错误状态、加载状态、移动端行为和可访问名称。
- 视觉调整必须保持公开/私有边界、URL、表单契约、权限校验和业务语义；行为变化需单独说明并获得确认。
- 页面之间共享的是设计语言和可验证的交互规则；只有在语义、状态和变化方向一致时才抽取组件。
- 每次优化控制在一个页面或一组强相关页面内，先完成真实页面验证，再进入下一组；不把全站重写混入单页优化。
- 页面验收至少覆盖桌面、窄屏、200%文字、键盘焦点、错误/空/加载状态、深浅主题和真实数据边界。
- 页面完成后更新对应的页面基线或验证报告；临时视觉草案不得成为当前规范入口。
